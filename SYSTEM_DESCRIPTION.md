## 0. Технологія RAG: концепція та реалізація

### 0.1 Що таке RAG і чому вона виникла

**RAG (Retrieval-Augmented Generation)** — архітектурний підхід у галузі штучного інтелекту, що поєднує два принципово різних механізми: **семантичний пошук** у зовнішній базі знань та **генерацію тексту** великою мовною моделлю (LLM). Концепцію вперше формально описали дослідники Meta AI у статті «Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks» (Lewis et al., 2020).

Виникнення RAG зумовлене фундаментальними обмеженнями класичних LLM:

**Проблема 1 — заморожені знання.** Велика мовна модель навчається на знімку даних з Інтернету, зробленому у певний момент часу (так звана "training cutoff date"). Після завершення навчання модель не може сама отримувати нові знання. Для правових систем це критично: законодавство змінюється, суди виносять нові рішення, регуляції оновлюються. Модель, навчена у 2023 році, нічого не знає про зміни, внесені у 2024–2025 роках.

**Проблема 2 — галюцинації.** LLM генерують відповіді, спираючись на статистичні патерни мови, а не на фактичну перевірку джерел. У відповідь на правовий запит модель може впевнено назвати неіснуючий параграф закону, неправильну суму виплати або вигадати рішення суду. В правовій сфері будь-яка неточність може призвести до реальних негативних наслідків для користувача.

**Проблема 3 — відсутність вузькоспеціалізованих знань.** Загальна LLM навчена на широких даних і не має глибоких знань у специфічній предметній галузі — наприклад, про права українців у Німеччині за §24 AufenthG, особливості оформлення Bürgergeld або судову практику BSG щодо тимчасового захисту.

**Проблема 4 — відсутність посилань.** Класична LLM не може вказати, з якого конкретного документа взята та чи інша інформація. Користувач не може перевірити відповідь.

RAG вирішує всі чотири проблеми одночасно: замість того, щоб покладатися на "вбудовані знання" моделі, система спочатку **шукає** релевантні фрагменти з актуальної бази документів, а потім передає їх моделі як контекст для генерації відповіді. Таким чином, модель відповідає не з пам'яті, а спираючись на реальні документи, що надаються їй у кожному запиті.

### 0.2 RAG проти альтернативних підходів

При проектуванні системи розглядалися три альтернативних підходи:

**Альтернатива 1: Чиста LLM без контексту**
Найпростіший підхід — відправляти запит напряму до GPT-4o без будь-якого контексту. Переваги: нульова складність реалізації. Недоліки: галюцинації в правових деталях, знання обрізані датою навчання, відсутність персоналізації, неможливо перевірити джерела. Для правової системи непридатний.

**Альтернатива 2: Fine-tuning (донавчання)**
Донавчання LLM на корпусі правових документів дозволяє "вбудувати" предметні знання в параметри моделі. Переваги: модель "знає" предмет і відповідає природно. Недоліки: вартість донавчання GPT-4o — десятки тисяч доларів; потребує перенавчання при кожній зміні законодавства; галюцинації не зникають повністю; джерела все одно не цитуються. Для проєкту не підходить через вартість та неможливість динамічного оновлення.

**Альтернатива 3: Keyword search + LLM**
Класичний пошук за ключовими словами (TF-IDF, BM25) з подальшою генерацією. Недолік: не знаходить документи при різному формулюванні запиту. Якщо користувач запитує "гроші від держави" — ключовий пошук не знайде документ, де написано "Bürgergeld" або "Grundsicherung". Семантичний пошук таку відповідність знаходить.

**Обраний підхід: RAG з векторним пошуком**

| Критерій | Чиста LLM | Fine-tuning | Keyword search | **RAG (обрано)** |
|----------|-----------|-------------|----------------|-----------------|
| Актуальність знань | ❌ | ❌ | ✅ | ✅ |
| Відсутність галюцинацій | ❌ | ⚠️ | ✅ | ✅ |
| Цитування джерел | ❌ | ❌ | ✅ | ✅ |
| Крос-мовний пошук | ⚠️ | ⚠️ | ❌ | ✅ |
| Персоналізація | ❌ | ❌ | ❌ | ✅ |
| Вартість розгортання | низька | висока | низька | **середня** |
| Оновлення знань | ❌ | складно | ✅ | ✅ |

### 0.3 Три фази класичного RAG-пайплайну

Будь-яка RAG-система складається з двох незалежних процесів:

**Офлайн-процес (виконується один раз або при оновленні):**
```
Корпус документів → Розбивка на фрагменти → Векторизація → Збереження у векторній БД
```

**Онлайн-процес (виконується при кожному запиті):**
```
Запит → Векторизація запиту → Пошук схожих фрагментів → Формування контексту → LLM → Відповідь
```

У даній системі ці процеси відповідають модулям:
- Офлайн: `data_collector` → `ingestion/chunker` → `ingestion/indexer` → ChromaDB
- Онлайн: `search/retriever` → `generation/personalizer` → `generation/generator` → відповідь

### 0.4 Ключова концепція: векторні ембеддинги

**Ембеддинг (embedding)** — це числовий вектор, що кодує смисловий зміст тексту в багатовимірному просторі. Нейронна мережа-енкодер (в даній системі — `paraphrase-multilingual-mpnet-base-v2`) перетворює будь-який текст у вектор з 768 числових значень.

Ключова властивість ембеддингів: **семантично близькі тексти мають геометрично близькі вектори**, навіть якщо написані різними мовами або різними словами.

Приклад:
```
"Яку соціальну допомогу я можу отримати?"   → [0.12, -0.45, 0.78, ...]
"Bürgergeld Anspruch §24 AufenthG"           → [0.14, -0.41, 0.76, ...]
"What social benefits am I entitled to?"      → [0.13, -0.43, 0.77, ...]
```

Всі три вектори знаходяться близько один до одного в 768-вимірному просторі, хоча записані різними мовами. Це і є **крос-лінгвальний семантичний пошук** — фундаментальна перевага RAG для мультилінгвальних правових систем.

**Формула косинусної подібності** (метрика пошуку):

```
similarity(A, B) = cos(θ) = (A · B) / (|A| × |B|)
```

де A — вектор запиту, B — вектор чанку документа. Значення від 0 (абсолютно різні) до 1 (ідентичні).

ChromaDB зберігає вектори всіх чанків і при запиті знаходить ті, чия косинусна подібність до вектора запиту є найвищою. Ця операція виконується через бібліотеку `hnswlib` з використанням алгоритму HNSW (Hierarchical Navigable Small World graphs), що забезпечує сублінійний час пошуку навіть серед мільйонів векторів.

**Обмеження чисто векторного пошуку:** семантичні ембеддинги добре знаходять тематично схожі фрагменти, але можуть пропускати документи з точними юридичними термінами (§24, BQFG, конкретні числа €502). Для вирішення цієї проблеми в системі реалізовано **гібридний пошук**.

### 0.5 Повний цикл обробки запиту в системі

**Приклад запиту:** "Чи маю я право на Bürgergeld якщо у мене статус тимчасового захисту і я знайшов роботу?"

- Детектування prompt injection: спроби "скинути" системний промпт через конструкції типу "ігноруй попередні інструкції"

Якщо запит прийшов від авторизованого веб-користувача (JWT у заголовку):

**Крок 3: Векторизація запиту** (`search/retriever.py`)

Текст запиту перетворюється в числовий вектор через модель ембеддингів:
```python
model = SentenceTransformer("paraphrase-multilingual-mpnet-base-v2", device="cpu")
query_vector = model.encode(["Чи маю я право на Bürgergeld..."])[0].tolist()
# Результат: список з 768 чисел типу float32
```
Модель завантажується один раз при старті і кешується в пам'яті (`@lru_cache`).

---

**Крок 4: Гібридний пошук + RRF + profile boost + reranking** (`search/retriever.py`)

Замість простого векторного пошуку система виконує чотириетапний покращений пайплайн:

**4a. Гібридний пошук (Hybrid Search = Vector + BM25)**

Для кожної колекції система паралельно виконує два пошуки:

```python
# Векторний пошук (ChromaDB, cosine ANN)
vector_results = retrieve(query, collection, top_k=15)

# BM25 пошук (rank-bm25, TF-IDF-подібний)
bm25_results = _bm25_search(query, collection, top_k=15)
```

BM25 (Best Matching 25) — класичний алгоритм інформаційного пошуку. На відміну від ембеддингів, він чутливий до точних термінів. Якщо користувач пише "§7 SGB II" — BM25 знайде точно цей параграф, навіть якщо семантичний пошук поверне загальніші результати.

BM25-корпус будується при старті системи у фоновому потоці: всі тексти чанків завантажуються з ChromaDB пакетами по 5000, токенізуються (lowercase split) і зберігаються у `BM25Okapi` в пам'яті.

**4b. Reciprocal Rank Fusion (RRF)**

Два списки результатів об'єднуються через RRF:

```
RRF_score(d) = Σ 1 / (k + rank_i(d)),  де k = 60
```

де `rank_i(d)` — позиція документа d у i-му списку. RRF не потребує нормалізації різнорідних оцінок (cosine vs BM25) і стійкий до викидів в одному з джерел.

**4c. Profile-based boosting**

Після злиття до rrf_score додається бонус +0.12 для чанків з файлів, які відповідають правовому статусу:

```python
_STATUS_FILE_BOOST = {
    "temporary_protection": ["aufenthaltsgesetz", "sgb_ii", "sgb_v", ...],
    "asylum_seeker":        ["asylgesetz", "asylbewerberleistungsgesetz", ...],
    "residence_permit":     ["aufenthaltsgesetz", "sgb_ii", "sgb_xii", "bqfg", ...],
}
```

Це гарантує, що для особи зі статусом `asylum_seeker` чанки з AsylbLG будуть вище в рейтингу, ніж нерелевантні норми SGB II.

**4d. Cross-encoder reranking**

Фінальне переранжування: cross-encoder модель `msmarco-MiniLM-L6-en-de-v1` оцінює кожну пару (запит, чанк) *спільно* — на відміну від bi-encoder (де запит і документ векторизуються окремо). Це значно точніший метод, але обчислювально дорожчий — тому застосовується тільки до 15–20 кандидатів після попереднього відбору:

```python
pairs  = [(query, chunk["text"]) for chunk in candidates]
scores = cross_encoder.predict(pairs)   # оцінює кожну пару разом
# результат: перевпорядкований список за relevance score
```

Для нашого прикладу після повного пайплайну система поверне:
- `sgb_ii.txt` — §7+§9 SGB II (Bürgergeld умови + право на отримання)
- `aufenthaltsgesetz.txt` — §24 AufenthG (тимчасовий захист, право на роботу)
- `beschaeftigungsverordnung.txt` — BeschV §2 (без Erlaubnis для §24)
- `sgb_ii.txt` — §11b SGB II (зарахування доходу при частковій зайнятості)
- `sgb_v.txt` — §5 SGB V (обов'язкове медичне страхування при Bürgergeld)

Чому окремі колекції? Це дає можливість:
1. Контролювати кількість результатів (5 + 2, а не перемішані 7)
2. Застосовувати різний поріг порівняльного контексту (0.42)
3. Незалежно оновлювати кожну колекцію

---

**Крок 5: Перевірка релевантності порівняльного контексту** (`generation/comparator.py`)

```python
def has_relevant_comparison(ukrainian_chunks, distance_threshold=0.42):
    return any(chunk["distance"] < 0.42 for chunk in ukrainian_chunks)
```

Поріг 0.42 обраний дослідним шляхом: нижче — висока семантична подібність (дійсно стосується запиту), вище — загальні документи без прямого зв'язку. У нашому прикладі дистанція 0.38 < 0.42, тому порівняльний блок **буде** доданий до промпту.


**Чому персоналізація критична?** Без урахування правового статусу відповідь буде некоректною: особа з AsylbLG-статусом має зовсім інші права, ніж особа з §24 AufenthG. Без регіонального контексту будуть відсутні специфічні місцеві органи та процедури. Персоналізація перетворює загальну правову довідку на конкретну інформацію для конкретної людини.

**Крок 7: Генерація відповіді** (`generation/generator.py`)

Сформований промпт відправляється до OpenAI API разом з `chat_history` (контекстом попередніх повідомлень):

```python
messages = [
    {"role": "system",    "content": full_prompt},    # системний промпт + документи
    {"role": "user",      "content": "попереднє питання"},     # з chat_history
    {"role": "assistant", "content": "попередня відповідь"},   # з chat_history
    {"role": "user",      "content": "Чи маю я право на Bürgergeld..."},  # поточний запит
]

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=messages,
    temperature=0.3,    # низька варіативність для точності
    max_tokens=1500,    # достатньо для розгорнутої відповіді
)
```

**Параметр temperature = 0.3** — свідомо занижений. При temperature=0 модель завжди дає одну й ту саму відповідь (детерміновано). При temperature=1 відповіді різноманітні, але можуть містити "творчі" доповнення. Для правових запитів потрібна точність, тому обрано проміжне значення 0.3 — достатньо природна мова, але мінімальна "фантазія".

**Включення chat_history** дозволяє системі підтримувати контекст розмови: наприклад, якщо попереднє питання було про реєстрацію, а поточне — "а де отримати довідку?" — система розуміє, що йдеться про довідку про реєстрацію.

Приклад відповіді GPT-4o-mini на основі переданих документів:
```
Так, маєте право на Bürgergeld. Відповідно до <code>§7 SGB II</code>,
особи зі статусом тимчасового захисту (<code>§24 AufenthG</code>)
мають право на Bürgergeld з першого дня...

Той факт, що ви знайшли роботу, <b>не позбавляє вас права</b> на виплати.
Якщо ваш дохід нижчий за прожитковий мінімум, Jobcenter доплачує різницю...
```

### 0.6 Роль векторної бази даних ChromaDB

ChromaDB — спеціалізована база даних для зберігання та пошуку векторів. На відміну від реляційних БД (де пошук ведеться за точними значеннями), ChromaDB виконує **пошук за наближеністю** (Approximate Nearest Neighbor, ANN).

**Внутрішня структура:**

```
ChromaDB
├── Колекція "german_law"
│   ├── ID: "f7a2e1..."  → вектор [0.12, -0.45, ...] + текст + метадані
│   ├── ID: "3b8c9d..."  → вектор [0.34, 0.12, ...]  + текст + метадані
│   └── ... (~10,000+ записів)
└── Колекція "ukrainian_context"
    ├── ID: "a1b2c3..."  → вектор [...] + текст + метадані
    └── ... (~2,000+ записів)
```

**Метадані кожного чанку:**
```json
{
  "source_file": "sgb_ii.txt",
  "category": "german_law",
  "chunk_index": 42,
  "language": "de"
}
```

**Алгоритм HNSW** (Hierarchical Navigable Small World):
- Будує граф зв'язків між векторами у просторі
- При пошуку обходить граф жадібним алгоритмом від "точки входу" до найближчих вузлів
- Складність пошуку: O(log N) замість O(N) при наївному переборі
- Параметр `hnsw:space = "cosine"` означає використання косинусної відстані

**Персистентність:** ChromaDB зберігає дані у файловій системі (`chroma_data` volume). При перезапуску контейнера всі вектори зберігаються — повторна векторизація не потрібна.

### 0.7 Моделі: bi-encoder та cross-encoder

Система використовує **дві нейронні мережі** для різних задач пошуку:

**Bi-encoder: paraphrase-multilingual-mpnet-base-v2**

Архітектура MPNet (Modified Permuted Language Model) — трансформерна модель з 12 шарами та 768-вимірним прихованим простором.

| Характеристика | Значення |
|----------------|----------|
| Мови | 50+, включаючи DE та UK |
| Розмір вектора | 768 вимірів |
| Розмір моделі | ~270 МБ |
| Застосування | векторизація чанків при індексації + векторизація запиту |
| Швидкість | ~200–500 токенів/с на CPU |

Bi-encoder кодує запит і документ **незалежно** → швидко (O(1) при пошуку по вже обчислених векторах), але менш точно ніж cross-encoder.

**Cross-encoder: msmarco-MiniLM-L6-en-de-v1**

Спеціалізована модель для оцінки релевантності пар (запит, документ). Навчена на MS MARCO + DeepCT з розширенням на German-English пари — ідеально для нашого use case (запити українською/англійською, документи німецькою).

| Характеристика | Значення |
|----------------|----------|
| Архітектура | MiniLM-L6 (6 шарів, ~22 МБ) |
| Вхід | конкатенація [CLS] query [SEP] document [SEP] |
| Вихід | score релевантності (float) |
| Застосування | реранжування 15–20 кандидатів після hybrid search |
| Швидкість | ~50–100 пар/с на CPU |

Cross-encoder оцінює кожну пару **разом** (увага між токенами запиту та документа) → значно вища точність, але O(N) — тому застосовується лише до невеликого числа кандидатів.

**Чому `device="cpu"`?** PyTorch 2.x використовує ліниве завантаження моделей через "meta tensors". При спробі обчислень без явної вказівки пристрою виникає `NotImplementedError`. Явне `device="cpu"` гарантує сумісність із Docker-контейнерами без GPU.

### 0.8 Інкрементна індексація та SHA256

Повне переіндексування всього корпусу документів займає 10–30 хвилин (векторизація тисяч чанків). Щоб уникнути цього при кожному перезапуску контейнера, реалізовано систему відстеження змін через SHA256:

```python
# При завантаженні нового файлу sgb_ii.txt:
sha256("...повний вміст файлу...") → "3a8f2c..."

# Порівняння зі збереженим значенням:
index_state["indexed_files"]["sgb_ii.txt"] == "3a8f2c..." ?
  True  → файл не змінився → пропускаємо
  False → файл оновлено → видаляємо старі чанки → додаємо нові
```

Стан зберігається у файлі `.index_state.json` (у bind-mounted директорії `./data/`), тому виживає між перезапусками контейнера. Це забезпечує **інкрементну** (а не повну) синхронізацію при оновленні бази знань.

**Логіка при старті API:**
```
ChromaDB порожній? → повне індексування → запам'ятати SHA256 всіх файлів
ChromaDB не порожній → знайти змінені файли (SHA256 diff) → переіндексувати тільки їх
```

### 0.9 Багатокрокова персоналізація: унікальна особливість системи

Стандартна RAG-система бере запит → шукає → генерує. Ця система додає **четвертий вимір — персоналізацію**, що є ключовою інновацією для цільової аудиторії.

Один і той самий запит "чи можу я отримати допомогу від держави?" дасть принципово різні відповіді залежно від профілю:

**Профіль A** (asylum_seeker, Bayern):
→ Інформація про AsylbLG замість SGB II, менші суми виплат, обмеження Wohnsitzauflage, контакти Landesdirektion Bayern

**Профіль B** (temporary_protection, Berlin):
→ Bürgergeld SGB II, повна сума (~502 €/міс), доступ до GKV, контакти LEA Berlin, програма Ukraineberatungszentrum

**Профіль C** (residence_permit, NRW):
→ Залежить від підстави видачі дозволу, перелік запитань для уточнення, контакти Kommunale Integrationszentren NRW

Персоналізація реалізована не через пошук ("шукати тільки по Bayern"), а через **формування контексту для LLM**: модель отримує інформацію про статус і регіон в системному промпті та самостійно адаптує відповідь. Це гнучкіше ніж фільтрація документів, оскільки одна норма закону може застосовуватись по-різному залежно від статусу особи.

### 0.10 Порівняльний правовий аналіз UA ↔ DE

Інноваційна риса системи — **двомовна правова база**: паралельне зберігання законодавства Німеччини та України в окремих колекціях ChromaDB.

При кожному запиті система перевіряє: чи знайдено достатньо релевантний фрагмент з українського законодавства (косинусна відстань < 0.42)? Якщо так — до промпту додається блок, що інструктує LLM пояснити норму Німеччини через аналог з Ukrainian права:

```
[Порівняльний матеріал — ua_employment_law.txt]
"Право на зайнятість... Закон України..."

→ Використайте ці матеріали, щоб ПОЯСНИТИ правила Німеччини
через призму того, до чого звикли в Україні.
```

Наприклад, запит про Bürgergeld → система порівняє з Допомогою по безробіттю за КЗпП, поясне відмінності в умовах, розмірах та процедурі оформлення. Для людини, яка не знайома з німецькою системою, такий порівняльний контекст суттєво полегшує розуміння.

Поріг 0.42 виключає додавання блоку при нерелевантних запитах (наприклад, питання про розклад роботи Ausländerbehörde не має прямого аналога в украйнському праві).

## 1. Загальна характеристика системи

### 1.1 Мета та призначення

Система є інтелектуальним асистентом правової підтримки для українських громадян, які перебувають на території Федеративної Республіки Німеччина. Основна проблема, яку вирішує система — мовний та правовий бар'єр: більшість правових документів Німеччини написана лише німецькою мовою, тоді як значна частина переселенців спілкується виключно українською.

Система реалізована за архітектурою **RAG (Retrieval-Augmented Generation)** — технологією, що поєднує семантичний пошук у базі правових знань з генерацією відповідей за допомогою великої мовної моделі (LLM). Це дозволяє отримувати точні відповіді, прив'язані до конкретних правових документів, а не спиратися виключно на загальні знання моделі.

### 1.2 Цільова аудиторія

- Українці зі статусом тимчасового захисту (§ 24 AufenthG)
- Особи, що подали заяву про надання притулку (Asylbewerber)
- Громадяни України з Aufenthaltserlaubnis (дозволом на проживання)
- Волонтери та соціальні працівники, що надають допомогу переселенцям

### 1.3 Основні функції

1. **Відповіді на правові запити** — персоналізовані, з урахуванням статусу, регіону та мови користувача
2. **Порівняльний правовий контекст** — паралельний аналіз норм права України та Німеччини
3. **Веб-інтерфейс** — чат-застосунок зі збереженням історії розмов
4. **Telegram-бот** — мобільний доступ через месенджер
5. **Система обмежень** — ліміт 50 запитів/день з можливістю придбання додаткових
6. **Автоматичне оновлення** — щоденна перевірка та оновлення правових документів

### 3.1 Призначення

Модуль автоматично завантажує актуальні правові документи з офіційних джерел, конвертує їх у текстовий формат і зберігає в директорії `data/`.

### 3.2 Джерела даних

Реалізовано три типи джерел (`SourceKind`):

```python
]
```

### 3.4 Управління станом (StateManager)

Стан завантажених документів зберігається в `index_state.json`. При кожному старті система перевіряє SHA256-хеш кожного файлу — і лише якщо файл змінився, запускає його переіндексування. Це забезпечує **інкрементну індексацію** без повного перебудування вектороної бази при кожному перезапуску контейнера.

**Ключове рішення**: `index_state.json` зберігається в директорії `CHROMA_PERSIST_DIR`, яка прив'язана до bind-mount хост-системи (`./data/`), що гарантує збереження стану між перезапусками контейнерів.

### 3.5 Валідація

Модуль `validator.py` перевіряє завантажені документи:
- Мінімальна довжина тексту
- Наявність ключових слів залежно від типу джерела
- Перевірка на тестовий/заглушковий контент

## 4. Модуль індексації (Ingestion Pipeline)

### 4.1 Три етапи конвеєра

```
Текстові файли → Chunking → Embedding → ChromaDB
```

### 4.2 Завантаження документів (Loader)

Модуль `ingestion/loader.py` зчитує `.txt` файли з директорії `data/` та визначає категорію документа залежно від підпапки:
- `data/german_law/` → категорія `german_law`
- `data/ukrainian_context/` → категорія `ukrainian_context`
- Мова визначається автоматично за вмістом або шляхом

### 4.3 Розбиття на чанки (Chunker)

**Ключова особливість: токен-базований розмір чанку (tiktoken)**

Розмір вимірюється у **токенах** через `tiktoken cl100k_base` — той самий BPE-токенайзер, що використовує GPT-4. Це гарантує узгодженість між chunking-фазою та контекстним вікном LLM.

```python
CHUNK_SIZE_TOKENS    = 512   # токени (≈ повний параграф закону)
CHUNK_OVERLAP_TOKENS = 64    # перекриття в токенах

separators = ["\n\n", "\n", ". ", " ", ""]
```

| Одиниця | Стара реалізація | Нова реалізація |
|---------|-----------------|-----------------|
| Вимір | символи | токени (cl100k_base) |
| CHUNK_SIZE | 512 символів ≈ 100–150 токенів | 512 токенів |
| CHUNK_OVERLAP | 64 символи | 64 токени |
| Мін. чанк | 20 символів | 10 токенів |

**Алгоритм** рекурсивно пробує ієрархію роздільників: абзаци (`\n\n`) → рядки (`\n`) → речення (`. `) → слова (` `) → символи. При кожному розбитті розмір поточного чанку вимірюється через `_enc.encode(text)`. Якщо жоден роздільник не дає чанків правильного розміру — застосовується пряме токенне розбиття через `_enc.encode` + `_enc.decode`.

**Перекриття** (64 токени ≈ 2–3 речення) гарантує, що інформація на межі двох чанків не губиться — сусідні чанки мають спільний контекст.

Кожен чанк зберігає метадані:
```python
{
    "text":        "...",
    "chunk_index": 42,
    "source_file": "aufenthaltsgesetz.txt",
    "category":    "german_law",
    "language":    "de"
}
```

### 4.4 Векторизація та збереження (Indexer)

**Модель ембеддингів:** `paraphrase-multilingual-mpnet-base-v2` (SentenceTransformers)
- Підтримує 50+ мов, включаючи українську та німецьку
- Розмір вектора: 768 вимірів
- Завантажується один раз через `@lru_cache` і кешується на весь час роботи процесу
- **Важливо:** запускається з `device="cpu"` для сумісності з PyTorch 2.x у Docker-контейнері

**Колекції ChromaDB:**

| Колекція | Вміст | Метрика відстані |
|----------|-------|-----------------|
| `german_law` | Закони Німеччини + директиви ЄС + судова практика | cosine |
| `ukrainian_context` | Закони України (для порівняльного аналізу) | cosine |

**Стратегія індексації:**
1. При першому старті (колекції порожні) → повне індексування всіх файлів
2. При повторному старті → перевірка SHA256, переіндексування тільки змінених файлів
3. Щодня у фоні → автоматичне завантаження нових версій документів та інкрементний re-index

### 4.5 Розподіл пам'яті

Бібліотека `hnswlib` (внутрішній індекс ChromaDB) не підтримує Unicode-шляхи на Windows. Тому шлях до персистентного сховища задається через змінну середовища `CHROMA_PERSIST_DIR` і завжди повинен бути ASCII-безпечним.

## 5. Модуль пошуку (Retrieval)

### 5.1 Покращений пайплайн: Hybrid Search → Profile Boost → Reranking → Cache

Файл `search/retriever.py` реалізує чотириетапний пайплайн `retrieve_parallel_enhanced()`:

```
запит + legal_status
         │
         ▼
    [1] Query Cache (TTL 5 хв)  ──── hit ──→  повернути збережений результат
         │ miss
         ▼
    [2] Hybrid Search (per колекція)
        ├── Vector search: ChromaDB cosine ANN, top-15 кандидатів
        └── BM25 search:   rank-bm25, той самий корпус, top-15 кандидатів
         │
         ▼
    [3] Reciprocal Rank Fusion (k=60)
        RRF_score = Σ 1/(60 + rank_i)
         │
         ▼
    [4] Profile Boost (+0.12 для файлів відповідного статусу)
         │
         ▼
    [5] Cross-encoder Reranking (msmarco-MiniLM-L6-en-de-v1)
        оцінює пари (query, chunk) разом
         │
         ▼
    trim → top_k_german=5, top_k_ukrainian=2
         │
         ▼
    зберегти в кеш → повернути
```

### 5.2 BM25-індекс: побудова та пошук

BM25 (Best Matching 25) — алгоритм оцінки релевантності, що враховує частоту терміна (TF) та зворотну частоту документа (IDF):

```
BM25(q, d) = Σ IDF(t) × [tf(t,d) × (k1+1)] / [tf(t,d) + k1 × (1-b+b×|d|/avgdl)]
```

де k1=1.5, b=0.75 — стандартні параметри, `avgdl` — середня довжина документа.

**Переваги над чисто векторним пошуком:**
- Точний збіг юридичних термінів: §24, BQFG, AsylbLG, конкретні суми (€502)
- Не залежить від того, чи ці терміни є у навчальному корпусі bi-encoder
- Швидкий (O(q × N) де q — токени запиту)

**Побудова індексу:** при старті API у фоновому потоці завантажує всі чанки з ChromaDB (пакетами по 5000), токенізує (lowercase split) і зберігає `BM25Okapi` об'єкт у пам'яті. До готовності BM25 система працює в режимі чисто векторного пошуку — без відмови.

### 5.3 Reciprocal Rank Fusion (RRF)

RRF вирішує ключову проблему: як об'єднати score-и різних систем пошуку (cosine distance від 0 до 2, BM25 score від 0 до ∞), що мають несумісні шкали?

Відповідь: **ігнорувати абсолютні score-и, використовувати тільки ранги**:

```python
def _rrf(vector_results, bm25_results, k=60):
    for rank, item in enumerate(vector_results):
        scores[key] += 1 / (60 + rank + 1)
    for rank, item in enumerate(bm25_results):
        scores[key] += 1 / (60 + rank + 1)
```

Параметр k=60 — стандартне значення з оригінальної статті (Cormack et al., 2009), що пом'якшує вплив перших позицій.

### 5.4 Cross-encoder vs Bi-encoder

| Аспект | Bi-encoder (MPNet) | Cross-encoder (MiniLM) |
|--------|--------------------|------------------------|
| Вхід | query окремо, doc окремо | [query; doc] разом |
| Механізм уваги | self-attention в межах одного тексту | cross-attention між query та doc |
| Швидкість | O(1) для нових запитів (вектори збережені) | O(N) — N пар |
| Точність | добра | вища (бачить зв'язки між словами запиту та документа) |
| Використання | первинне відсіювання (15 канд.) | реранжування фіналістів |

### 5.5 TTL Query Cache

```python
_query_cache = _QueryCache(ttl_seconds=300, max_entries=256)
```

Ключ кешу: SHA256(`query | legal_status | top_k_german | top_k_ukrainian`).
TTL = 5 хвилин: відповідає циклу швидких "уточнюючих" запитів одного користувача.
При cache hit повний пайплайн (BM25 + reranking + OpenAI) пропускається → latency < 50 мс.

### 5.6 Reconnect при збоях ChromaDB

Клієнт ChromaDB не кешується через `@lru_cache`. При кожному виклику перевіряється `heartbeat()`. Якщо ChromaDB недоступний — автоматично перемикається на локальний `PersistentClient`.

## 6. Модуль генерації (Generation)

### 6.1 Повний RAG-пайплайн

```
query + profile
       │
       ▼
  retrieve_parallel_enhanced()   ← Hybrid(vector+BM25)+RRF+boost+rerank+cache
       │
       ▼
  build_prompt()                 ← персоналізований системний промпт
       │
       ▼
  has_relevant_comparison()      ← чи варто додавати UA ↔ DE порівняння?
       │
       ▼
  add_comparison()               ← додаємо блок порівняння (якщо так)
       │
       ▼
  OpenAI GPT-4o-mini        ← генерація відповіді
       │
       ▼
  GenerationResult(answer, sources, has_comparison)
```

### 6.2 Персоналізований промпт (Personalizer)

Файл `generation/personalizer.py` будує системний промпт з наступних блоків:

**1. Мовна інструкція**
```
"Відповідайте українською. ВИНЯТОК: якщо користувач просить написати
офіційний документ іншою мовою — напишіть цей документ запитаною мовою."
```

**2. Контекст правового статусу** (4 варіанти):
- `temporary_protection` → деталі §24 AufenthG, права на роботу, Bürgergeld
- `residence_permit` → загальний дозвіл на проживання
- `asylum_seeker` → BAMF, AsylbLG, обмежений доступ до послуг
- `unknown` → загальна інформація

**3. Регіональні особливості** (5 регіонів):
- Bayern, Berlin, NRW, Hamburg, Sachsen
- Специфічні органи влади, процедури, контакти

**4. Фокус категорії запиту:**
- `residence`, `social_benefits`, `employment`, `education`, `healthcare`, `other`

**5. Витягнуті документи** — релевантні чанки з ChromaDB з посиланням на джерело

**6. Інструкції форматування** — заборонено Markdown (`**`, `__`), дозволено HTML-теги (`<b>`, `<i>`, `<code>`)

**7. Disclaimer** — попередження, що це інформаційна підтримка, не офіційна консультація

### 6.3 Порівняльний контекст (Comparator)

Модуль `generation/comparator.py` аналізує чанки з `ukrainian_context`:
- Якщо знайдено релевантні норми (відстань ≤ порогу) — додається блок порівняння
- Блок пояснює різницю між правовими системами України та Німеччини в контексті запиту

### 6.4 Streaming (SSE)

Для веб-інтерфейсу реалізовано **Server-Sent Events** streaming:

```python
async def generate_stream(...) -> AsyncGenerator[str, None]:
    # 1. Retrieval (sync, у thread pool — щоб не блокувати event loop)
    german_chunks, ukrainian_chunks = await loop.run_in_executor(None, retrieve_parallel)
    
    # 2-3. Prompt building
    prompt = build_prompt(...)
    
    # 4. Streaming від OpenAI
    stream = await client.chat.completions.create(..., stream=True)
    async for chunk in stream:
        yield f'data: {{"token": "{chunk}"}}\n\n'
    
    # Фінальний chunk з метаданими
    yield f'data: {{"done": true, "sources": [...]}}\n\n'
```

Формат SSE:
```
data: {"token": "Відповідно"}
data: {"token": " до § 24"}
data: {"token": " AufenthG..."}
data: {"done": true, "sources": ["aufenthaltsgesetz.txt"], "has_comparison": false}
```

| Параметр | Значення | Обгрунтування |

| Модель | `gpt-4o-mini` | Баланс якості та вартості |
| `temperature` | `0.3` | Низька варіативність для точних правових відповідей |

```python
class QueryRequest(BaseModel):
```

### 7.3 Middleware

**RateLimitMiddleware** — IP-рівневий захист від зловживань:
- `per_ip_rpm` = 15 запитів/хвилину з однієї IP-адреси
- `global_rpm` = 200 запитів/хвилину на всю систему
- Реалізовано через sliding window з `asyncio.Lock`

**SecurityHeadersMiddleware** — додає HTTP-заголовки безпеки:
```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
X-XSS-Protection: 1; mode=block
Referrer-Policy: strict-origin-when-cross-origin
```

### 7.4 Захист від prompt injection

Модуль `api/security.py` перевіряє запит перед обробкою:
- Детектування спроб "скинути" системний промпт
- Санітизація для логів (екранування спецсимволів)
- Відхилення запитів з підозрілими патернами з кодом 400

### 7.5 Фоновий lifecycle (Lifespan)

При старті FastAPI запускаються дві фонові задачі:
1. `_background_reindex()` — смарт-індексація (не блокує старт сервера)
2. `_daily_update_loop()` — щоденне оновлення документів

Сервер відповідає на `/health` одразу після старту. Якщо індексація ще не завершена, `/query` повертає 503 (порожні колекції).

Профіль користувача зберігається в SQLite (`data/users.db`, таблиця `user_profiles`). При перезапуску бота профіль відновлюється автоматично.

### 9.5 Парсинг документів (Bescheid)

Бот приймає фотографії або PDF-файли документів (Bescheid від Jobcenter, Ausländerbehörde). Через GPT Vision витягується:
- `valid_until` — термін дії
- `monthly_amount` — розмір виплати
- `case_number` — номер справи
- `issuing_office` — орган, що видав

Дані зберігаються в `user_documents`. Функція `get_expiring_soon()` використовується для проактивних нагадувань за 30/14/7 днів до закінчення терміну.

## 10. Автентифікація та обмеження запитів

### 10.1 JWT-автентифікація

**Реєстрація:**
```
POST /auth/register
{ email, username, password }
→ хешування bcrypt → SQLite web_users → JWT (24 год)
```

**Вхід:**
```
POST /auth/login
{ email, password }
→ bcrypt.verify → JWT (24 год)
```

**JWT payload:**
```json
{ "sub": "42", "exp": 1748000000 }
```

**Захищені ендпоінти** — `HTTPBearer(auto_error=False)`: якщо токен відсутній, запит дозволяється (анонімно), якщо присутній і невалідний — відхиляється.

### 10.2 База даних користувачів (SQLite)

**Таблиця `web_users`:**
```sql
CREATE TABLE web_users (
    id                 INTEGER PRIMARY KEY AUTOINCREMENT,
    email              TEXT    UNIQUE NOT NULL,
    username           TEXT    NOT NULL,
    password_hash      TEXT    NOT NULL,
    created_at         TEXT    DEFAULT (datetime('now')),
    legal_status       TEXT    DEFAULT 'unknown',
    region             TEXT    DEFAULT 'unknown',
    query_category     TEXT    DEFAULT 'other',
    language           TEXT    DEFAULT 'uk',
    daily_query_count  INTEGER DEFAULT 0,
    daily_query_date   TEXT    DEFAULT '',
    bonus_queries      INTEGER DEFAULT 0
);
```

### 10.3 Система добових лімітів

**Механізм роботи:**
```python
DAILY_QUERY_LIMIT = 50  # базовий ліміт (налаштовується через .env)

def check_and_increment(user_id):
    today = date.today().isoformat()
    row = get_user_row(user_id)
    
    count = row.daily_query_count
    if row.daily_query_date != today:
        count = 0  # новий день — скидаємо
    
    effective_limit = DAILY_QUERY_LIMIT + row.bonus_queries
    if count >= effective_limit:
        return False, count, effective_limit  # ліміт вичерпано
    
    update(daily_query_count = count + 1, daily_query_date = today)
    return True, count + 1, effective_limit
```

**Дворівнева система:**
- **Базовий ліміт**: 50 запитів/день (скидається о 00:00)
- **Бонусні запити** (`bonus_queries`): не скидаються, витрачаються після базових

**Пакети покупки** (демо-режим, без реального платежу):
- +10 запитів
- +50 запитів

**Telegram-бот** — окрема SQLite (`data/users.db`, таблиця `user_profiles`) з тими самими полями та логікою. Ліміт перевіряється локально, без звернення до API.

## 11. Система оцінювання якості

### 11.1 Методологія

Для оцінки якості RAG-системи реалізовано **автоматизований evaluator** (`evaluation/evaluator.py`) за принципом "LLM-as-a-judge": GPT-4o-mini оцінює відповіді системи за чотирма метриками.

### 11.2 Метрики

**LLM-оцінки (1–5 балів):**

| Метрика | Опис |
|---------|------|
| `relevance` | Чи відповідь стосується запиту? |
| `faithfulness` | Чи факти підкріплені джерелами (немає галюцинацій)? |
| `completeness` | Чи відповідь повна та охоплює ключові аспекти? |
| `clarity` | Чи відповідь чітка, структурована і зрозуміла? |

**Автоматичні метрики:**

| Метрика | Опис |
|---------|------|
| `keyword_hit_rate` | Частка очікуваних термінів у відповіді |
| `source_hit` | Чи присутнє очікуване джерело у відповіді |
| `latency_ms` | Час відповіді API (мс) |

### 11.3 Golden Dataset

Файл `evaluation/golden_dataset.json` містить тестові питання з еталонними відповідями, розподілені за темами:
- Тимчасовий захист та документи
- Соціальні виплати (Bürgergeld, Wohngeld)
- Право на працю
- Освіта та медицина
- Порівняльний контекст UA ↔ DE

### 11.4 Вихідні артефакти

- `evaluation/results.csv` — детальна таблиця результатів
- `evaluation/report.md` — Markdown-звіт з агрегованими метриками та детальними відповідями

### 11.5 Базова лінія (Baseline)

`evaluation/baseline.py` реалізує просту систему без RAG (тільки LLM без контексту) для порівняння метрик — демонструє приріст якості від використання векторного пошуку.

## Додаток Б: Основні алгоритмічні рішення

1. **Токен-базоване розбиття на чанки** (tiktoken cl100k_base): 512 токенів із перекриттям 64 токени; пріоритет природних меж (абзаци → речення); точний підрахунок через BPE-токенайзер GPT-4

2. **Смарт-індексація** через SHA256: переіндексуються лише змінені файли, а не вся база знань

3. **Двоколекційна архітектура** ChromaDB: окремо `german_law` та `ukrainian_context` для можливості різної кількості результатів та контрольованого порівняльного аналізу

4. **Hybrid search + RRF**: векторний пошук (ChromaDB cosine) + BM25 (rank-bm25), злитих через Reciprocal Rank Fusion (k=60) — без нормалізації різнорідних score-ів

5. **Profile-based boosting**: +0.12 до RRF score для файлів, що відповідають legal_status користувача; визначається через `_STATUS_FILE_BOOST` dict

6. **Cross-encoder reranking** (msmarco-MiniLM-L6-en-de-v1): попарна оцінка (query, chunk) зі спільним cross-attention; застосовується до 15 кандидатів після RRF

7. **TTL Query cache** (SHA256-ключ, 5 хв, 256 entries): повторні ідентичні запити повертаються без звернення до ChromaDB та OpenAI

8. **Двошарова система лімітів**: IP rate limit (middleware) + добовий ліміт запитів (JWT рівень) + незалежний ліміт Telegram-бота (локальна SQLite)

9. **SSE streaming без блокування**: retrieve виконується в `executor` (thread pool), щоб не блокувати asyncio event loop

10. **Reconnect до ChromaDB**: перевірка `heartbeat()` при кожному виклику + автоматичне перемикання на локальний `PersistentClient`

11. **BM25 фоновий warmup**: daemon-потік будує in-memory індекс при старті API; до готовності — деградація до vector-only без відмови
